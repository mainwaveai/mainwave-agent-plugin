# Mainwave agent plugin

The Mainwave plugin for Claude Code and Cowork. It reports Claude sessions to [Mainwave](https://mainwave.com) so an organization can see what its Claude work costs and what it is for.

It is a Claude Code mod: TypeScript that runs inside Claude Code and Cowork. Nothing needs installing on the machine: no Node, Python or CLI.

> [!IMPORTANT]
> Requires Claude Code 2.1.317 or later, in every place a session runs: a remote machine, a script, an IDE extension or the desktop app can run an older copy than the terminal does. `claude --version` shows the version; `claude update` updates a native install, and other installs update through their package manager. Older versions send less or nothing; see [Install](#install).

## What it does today

The plugin does five things.

**It stamps Claude Code's rows.** Where an organization already sends Claude Code's OpenTelemetry to Mainwave (the managed `env` block from Mainwave's org-wide setup), the plugin adds four attributes to every log row Claude Code exports that names an organization:

| Attribute | Value |
| --- | --- |
| `mainwave.plugin.name` | `mainwave` |
| `mainwave.plugin.version` | the plugin's version, such as `0.1.0` |
| `mainwave.plugin.entrypoint` | where the session runs, from `CLAUDE_CODE_ENTRYPOINT` (`cli`, `claude-vscode`, `remote_cowork` and so on); `other` for anything else |
| `mainwave.telemetry.route` | which path the row took: `exporter` on the row Claude Code's exporter sends, `plugin` on the plugin's own copy |

Mainwave can then tell which sessions run the plugin, which version, and where. It stamps only the rows that reach it: since Claude Code 2.1.328, in Team and Enterprise organizations, none do (Two modes, under What it sends), so there it stamps nothing, and its own copy is what reaches Mainwave.

It also reads who the session is from those rows: the organization (`organization.id`), the account (`user.account_uuid`), the email (`user.email`) and the device (`user.id`, an ID Claude Code keeps per installation). It keeps them in memory for the session. Where no row reaches the plugin (`rows_skipped` and Two modes, below), it reads them where Claude Code reads them, unless the session signs in with a key or a provider of its own (an API key or token, a gateway's token, a cloud provider, an `apiKeyHelper`): then none. First from the variables a host sets to name the session's account (`CLAUDE_CODE_ORGANIZATION_UUID`, `CLAUDE_CODE_USER_EMAIL`, `CLAUDE_CODE_ACCOUNT_UUID`; Cowork sets them), which also hold where the host hands the session its OAuth token. Otherwise, where the session signs in with the account file's login (no API key, cloud provider, gateway or host token), from Claude's account file (`oauthAccount` and `userID` in `.claude.json`, in `CLAUDE_CONFIG_DIR`, else the home folder). The device ID comes from that file alone. It is read even where the session signs in another way or with a key, as Claude Code keeps it per installation, not per login. It uses them until a row names the session, and reads nothing else in that file for it. The organization and email go to Mainwave in two places only: on the records of its own copy (below), and in its request for the organization's settings (next). The account and device go on the copy's records alone.

**It asks Mainwave for the organization's settings.** Once a row names the organization and email, the plugin asks Mainwave which data points the organization turned on or off and which redaction packs it runs, applies the answer to what it sends (what its settings page shows: Mainwave's defaults, today every data point on, for those the organization left alone), keeps it in its store for later sessions, and asks again every 4 minutes, within the 5 minutes Mainwave's settings page promises. See The organization's settings, under What it sends.

**It sends its own copy, to Mainwave's production collector.** So an organization needs nothing but the plugin. The plugin sends a copy of a session's log rows, spans and metrics to `https://collector.mainwave.com` (`/v1/logs`, `/v1/traces` and `/v1/metrics`), and nowhere else, without a key, routed by the Claude organization and email on each record (see Keyless, below). Only the person's own settings can send it elsewhere, such as to Mainwave's dev collector (see Settings). Where the organization's `env` block is in place, Claude Code's exporter goes on sending the originals wherever the organization pointed it, so nothing is counted twice, and the two can be compared record for record. Without it, the plugin's copy is all that is sent.

- **Log rows** are copies: the exporter's row as Claude Code raised it, with the same attributes (identity, `event.name`, `event.sequence`, `event.timestamp`) less those the settings hold back (What it sends), the same time and the same trace and span IDs. Where Claude Code's row names no span but the plugin builds the trace (below), the copy carries the IDs of the span it ran in, as Claude Code's rows do when it traces.
- **Spans and metrics are rebuilt.** They never pass through a plugin: the one hook Claude Code gives plugins for its telemetry carries log rows alone. So the plugin puts them back together from what it does see: the rows, and Claude Code's own events for turns, model requests, tool calls and subagents. What it sends has the exporter's names, attributes, attribute order and value types, and the exporter's trace IDs; the table below says where each comes from.
- **Every record** carries `mainwave.telemetry.route` set to `plugin`, and a record built without Claude Code's rows (below) carries `mainwave.telemetry.built_from` set to `events`. While the person has opted in to data points that are off by default (see Settings), every log row and span also carries `mainwave.telemetry.opt_in`, listing them. The resource is rebuilt as the exporter builds it (`service.name`, `service.version`, then `OTEL_RESOURCE_ATTRIBUTES`, then `OTEL_SERVICE_NAME`), and each signal goes as OTLP/JSON under the exporter's own scope for it.

| What Claude Code sends | What the plugin rebuilds it from |
| --- | --- |
| `claude_code.interaction`, one per turn of the main conversation, and one per slash command that asks no model (`/plugins`, `/cost`, `/exit`) | Its trace and span IDs are the `user_prompt` row's. A turn's end is the turn's end, and its start that less the turn's duration; a command's runs from the command's start to its end |
| `claude_code.llm_request`, one per model request | The request's `api_request` (or `api_error`) row: model, tokens, request ID, time to first token, effort, query source. The request's own stream gives its start and stop reason. Its parent is the row's span |
| `claude_code.tool`, one per tool call | The tool call itself: its name, its input (the command, file, skill or agent type, where the data they belong to is on: see What it sends), what it answered (the `tool.output` event) and its time. Its parent is its `tool_result` row's span |
| `claude_code.tool.blocked_on_user`, the call's permission decision | The `tool_decision` row: its trace and span IDs, the decision and its source |
| `claude_code.tool.execution`, the call's run | The call's time and its `tool_result` row's outcome, error and error class. An Agent call's takes its span ID from its subagent's rows |
| `claude_code.cost.usage`, `claude_code.token.usage` | Each `api_request` row's cost and tokens |
| `claude_code.lines_of_code.count` | Each Edit and Write call's result: its patch, or the whole file written |
| `claude_code.commit.count`, `claude_code.pull_request.count` | Each Bash command that succeeded, read by Claude Code's own rules (`git commit`, `gh pr create`, `glab mr create` and so on), and each MCP tool named for creating a pull request. A command run through an MCP shell tool (Cowork's `device_bash`) counts as a Bash command |
| `claude_code.code_edit_tool.decision` | Each `tool_decision` row of an Edit, Write or NotebookEdit call |
| `claude_code.active_time.total` (`type` `cli`) | Each interaction's duration, a turn's or a command's |
| `claude_code.session.count` | The session's start |

**With and without the env block.** Claude Code ties its rows to its spans only when it traces, which Mainwave's `env` block turns on (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`, with a traces exporter). Without it, Claude Code still hands the plugin every row and every event, but no row names a span, and there are no exporter spans to mirror. So the plugin decides once per load, from that variable (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`, else `ENABLE_ENHANCED_TELEMETRY_BETA`, as Claude Code reads it):

- **On: it mirrors the exporter**, ids and all, as the table above says, for every turn whose prompt row names its span.
- **On, but a turn's prompt row names no span: it rebuilds that turn.** This is the first turn of a session a host drives through its SDK (such as T3 Code) where the env block arrives with the organization's managed settings: the turn begins before Claude Code traces, so it sends no interaction, and each of the turn's requests and tool calls as a trace of its own. The plugin sends the turn as one trace instead, the same shape as below: its own interaction as the root, the requests and calls under it. The span IDs the rows do name (each permission decision's, a subagent's) are kept, and the trace Claude Code started for each call is moved onto the interaction's, with everything in it (the call's decision and run, its subagent, a skill it loaded). The turns after it are traced, and mirrored.
- **Off, and no row has named a span: it builds the trace itself.** Each interaction is the root of a trace of its own, started as the turn (or the slash command) starts. The turn's model requests and tool calls are its children, each call's `blocked_on_user` and `execution` spans the call's, and a subagent's requests and calls are children of its Agent call's `execution` span, nested subagents included. Every id is the plugin's own. A request outside the main loop and its subagents (a session title, a summary) is a root, as the exporter sends it. If a row ever names a span after all, the plugin goes back to mirroring from then on.

Every span and data point starts with the attributes Claude Code puts first on all its records (the session's identity, the organization's resource attributes, the repository): the plugin takes them from the latest row, everything before its `event.name`. Metrics are monotonic sums with delta temporality, as Claude Code sends them: summed between collections, collected every `OTEL_METRIC_EXPORT_INTERVAL` milliseconds (a minute unless set) and once more as the session ends.

**Two modes: with Claude Code's rows, or built from its events.** The plugin picks one per load by itself, and needs no setting for either.

- **Without them**, it builds the rows from Claude Code's own events. This is its main path: Claude Code and Cowork alike, in Team and Enterprise organizations. Since 2.1.328, there and on machines with managed settings, Claude Code seats a built-in plugin that runs first. It sends every collector row, and every classic hook event, on past the plugins in the `user` tier. An org-synced plugin is one, Required or not, and so is one the organization's managed settings enable from this repository. Claude Code seats a plugin in the organization's tier only from a marketplace in a local folder, or, from a remote source, once it records a hash of the plugin's copy, which 2.1.328 does not yet. The plugin's other hooks still run, so it builds from turns, model requests, responses, tool calls, permission checks and the session's cost.
- **With rows**, it copies Claude Code's own rows, as above. This happens where they reach it: a personal account, and Claude Code before 2.1.328.

The plugin builds rows when no row of Claude Code's has reached it by the time the first turn of a load begins. Claude Code 2.1.326 and later hands each plugin a row as it loads, and a turn's prompt row before its turn, so where rows reach the plugin one has come by then. A row seen earlier in the same process, before a reload, counts too. On an older Claude Code, the grace of `rows_skipped` decides instead, and the rows are built from the next turn on, never from the middle of one. The first row of Claude Code's that reaches the plugin ends it for the load, and from then the rows are copies again. So no record is sent twice, and a session's status row says which mode it ran in: `rows_skipped` while it builds them.

| Row | When | What it carries |
| --- | --- | --- |
| `user_prompt` | A main-loop turn begins with a prompt (not a continuation) | The prompt's length, and its text where `prompt.text` is on; Claude Code's `prompt.id` for it, which the turn's other rows carry too |
| `api_request` | A model request answers | From `turn.step`: the model, the four token counts and the cache writes by lifetime, and the effort. A subagent's `query_source` and `agent.name`, from its spawn. Its duration and time to first token, on the plugin's clock. Its cost: what the session's cost (`$.session.usage()`) grew by since the request before |
| `assistant_response` | A model request answers with text, after its request row | The response's length and its text (where `response.text` is on), from the step's own answer; its model and `query_source`, and a subagent's `agent_id` |
| `tool_decision` | A tool call settles, timed at its start | `reject` where the call was refused: its permission check (`tool.check`) refused it, or asked, and the call then ended in Claude Code's text of a refusal (the person's, the one for an ask no one could answer, or the ask's own reason). Else `accept`. Its `source` where the check names a rule or a setting (`config`) or a hook (`hook`), and its `tool_source` |
| `tool_result` | A tool call that was not refused ends | Its outcome and duration, its input's and result's sizes in bytes, and its parameters and input where their data points are on |

**Content.** The prompt, the response and the tool input go on the built rows from the plugin's own hooks (`prompt.submit` and `turn.start`, `turn.step`'s stream, `tool.call`), each where its data point is on, through the same gate and redaction packs as a copied row. Like the rest of the content, they are all off unless the organization's settings, or the person's own opt-in, turn them on. The tool output goes on the tool spans as with rows (`tool.result`), and the thinking on the request spans (`response.thinking`). In Cowork, whose own export always leaves this content out, these rows are the only way it reaches Mainwave. A stream's text goes on one response row only: a row of Claude Code's that comes later fills nothing from it.

Every row starts as Claude Code's do: the organization's resource attributes, the device, the session and who it is, then `anthropic.provider`, `anthropic.custom_base_url` where `ANTHROPIC_BASE_URL` is set, and `terminal.type` `non-interactive` for a session no person types into. The rows go through the rebuild and the copy as Claude Code's rows do, so the spans and metrics go with them. Each interaction is the root of a trace the plugin builds, as without the env block. They go under the identity above: the host's variables, else the account file. What the session spends between turns, or after the last one, goes in `cost.usage` with `query_source` `auxiliary`, as the exporter sends the cost of requests outside the main loop. Examples are a compaction, a prompt suggestion or a memory. So the session's cost there is Claude Code's whole. What it spends during a turn outside a request of it goes with that turn's next request.

**What Claude Code's rows add.** The end-to-end test runs the same scripted session in both modes and compares the plugin's two copies field by field (Developing, below). The rows built from events carry every other field the copied rows carry, with the same values. What the copy with Claude Code's rows has besides, where rows reach the plugin:

| Only with Claude Code's rows | Why the built rows lack it |
| --- | --- |
| The other rows: `api_error`, `subagent_completed`, `plugin_loaded`, `mcp_server_connection`, `permission_mode_changed`, `retention_sweep` and the rest | No event a plugin may hook carries them |
| A request's `request_id` (on its row and span, and as the span's `gen_ai.response.id`), on its response, decisions and results too, and its `speed` | `turn.step` does not report them |
| A decision's `permission_mode`, and its `source` where the person, the mode or the classifier settled an ask | No event a plugin may hook says it |
| A failed call's `error_type`, and so its run span's `error_class`, and its `error` unless the call's output goes (`tool.result`) | Claude Code names the error's class, which the call's result does not |
| A prompt or response row's `message.uuid` | No event a plugin may hook says it |
| The tokens of model requests outside a turn: memory extraction, prompt suggestions, compaction, summaries, a web page's reading, session titles, classifiers | They are not steps of a turn, and no event a plugin may hook shows them. Their cost is counted (above), not their tokens or model. In two weeks of sessions Mainwave received in November 2026, these requests were about 9% of requests and 4% of the cost. They were 5% of the tokens (5% of output and cache reads, 2% of cache writes), and nearly all of the uncached input, which a turn's requests mostly read from the cache. Per session, the median share of the cost was under 0.1%, and one in ten sessions was above 10% |
| A request that brought no response | Claude Code's `api_error` row says what failed; no event does |
| The request's own duration and time to first token | The plugin times a request from the start of its step, a retry's wait included, to the first piece of its stream |
| Each request's own share of a turn's cost | A request's cost is what the session's grew by since the reading before, the readings taken one at a time, so the shares never sum past the session's cost. Requests that end together (subagents running at once) may trade shares, and a cost outside a request during a turn lands on the next request. Where the session began well before the plugin loaded (a resume, a reload), what it had cost by then is not counted again |
| An interactive session's `terminal.type` | Claude Code reads the terminal from its own environment |
| A call the check asked about and something else refused (a hook on the permission request, auto mode's classifier) reads as accepted and failed | A refused call ends in an error, as a failed one does: the plugin knows Claude Code's own texts of a refusal alone. The event that says an ask was allowed (`tool.run`) is newer than the plugin's floor, which refuses a module that hooks it |

- **Keyless:** the plugin sends no `Authorization` header (one would send the request down the key path, where it is refused). The collector routes each request by the `organization.id` and `user.email` on every record, span and data point in it (never the resource's), one pair per request. So the plugin queues only records that carry both, each of the right shape: a session on an API key or a cloud provider names no organization or email, and its records are held back: never queued or sent, and dropped from an outbox an earlier session left when this one takes it over. Each batch holds one pair's records alone, so a batch the collector refuses holds back or drops no one else's. A refusal of the pair (403, reason `unclaimed`: no Mainwave workspace has claimed the Claude organization; `email_domain`: the email's domain is not one the workspace accepts) stops sending that pair's records until the plugin loads again: those already queued are kept for a later load, and no more are queued this load; other pairs, from outboxes earlier sessions left, go on. Any other refusal of the whole request stops sending for the load (below).
- **A collector that takes no keyless rows** (one the person's settings name with keyless ingest off, say) answers 401, or a 403 that names no reason. The plugin then stops sending for the load, queues nothing more and takes over no other session's outbox: what it had queued is kept for a later session, which tries once more. So a session makes one refused request (up to one per signal, when it ends before its first timed send), not one every few seconds. What a machine keeps grows only by what each session queues before its first send, a few seconds of rows, and never past the queue's caps (below).
- **How it goes:** the hooks only queue. A timer sends the queue in batches of up to 200 records of one signal every 5 seconds, and the end of a session sends one more batch of each signal at once. After a network failure, a timeout or a busy collector, the batch goes back in the queue, and the wait before that signal's next try doubles, up to a minute; each try waits a random share of that wait, so machines turned away together come back apart. A collector that answers 429 or 503 with `Retry-After` is left alone at least that long (up to ten minutes), plus up to a fifth more at random. The other signals go on. These waits last for the load: a session that starts later tries at once. A path the collector does not have (404) is not tried again until the plugin loads again, and its records are kept. A batch the collector refuses as malformed, or that cannot be written as a request, is dropped. A refusal of the whole request stops sending, and queuing, until the plugin loads again. A span waits up to 2 seconds for the event it pairs with, then goes with what it has.
- **Sent once:** each batch carries an `idempotency-key` header, made when the batch is first formed and kept through every retry. A retry carries the same records under the same key. Past the queue's caps, only the oldest records the caps need are dropped; if one was in a batch, the rest of that batch goes again under a new key, which may store it twice but never loses it. The collector stores a batch whose key it has already taken only once, so a batch that may have landed (a timeout, a request cut off as the session ended) is sent again, metrics included. A batch has a hash of its organization and email in its key. A batch an earlier version formed with a dev ingest key, kept in an outbox, goes keyless as one batch per person, each with that person's hash after the key, so it may be stored twice, but is never lost.
- **What survives:** the queue, all three signals together, is kept in the plugin's store (about 1 MB at most, a few hundred to a few thousand records, oldest dropped first), saved at most every 10 seconds and at session end, so records a session could not send are sent by a later one, in the same batches under the same keys. Past the caps, a batch is never sent in part under its key: what is left of it goes under a new key, which may store it twice, never lose it. A process that dies loses at most the last 10 seconds or so of copies, and the metrics since their last collection. The end of a session is short (Claude Code gives all of a session's end hooks 1.5 seconds together), so the last batches may be sent by the next session instead.

**It sends the markers Mainwave's CLI hooks send.** Claude Code's telemetry records that a commit, a pull request or a ticket save happened, not which one; nor the account's plan and limits, nor the kind of API error a turn ended on. Mainwave's CLI hooks send those as spans of their own (markers), with an ingest key. The plugin sends the same spans, keyless through its copy, so an organization on the plugin alone, with no CLI and no key, still gets them. It makes them from Claude Code's own hook events (a tool call that ended without error, a prompt that entered, a main-loop turn's end), never from the classic hook events (PostToolUse, UserPromptSubmit, StopFailure): Claude Code's security default, seated for Team and Enterprise organizations, wherever managed settings are, and in remote Cowork, skips every classic hook of a plugin a person installs or an organization syncs.

| Marker | When | What it carries | Its key, and that key's data point |
| --- | --- | --- | --- |
| `vcs.commit.created` (`hook.git`) | A Bash command printed git's line for a new commit (`[main 1a2b3c4] ...`): a failed or quiet commit makes none | The commit's full name and first parent, its parent count, and its files and lines in all and per file, from `git show --numstat`, run where the command ran. Never a file's contents, the diff or the message | `vcs.commit.sha`, `repo` |
| `vcs.change.opened` (`hook.github`) | `gh pr create`, as a command of its own, printed the new pull request's address (not one that says it already exists) | Its address and number, the title the command wrote out (`--title`, `-t`; none where the shell would expand it), and its files and lines from `gh pr view <address> --json changedFiles,additions,deletions` | `vcs.repository.url.full`, `repo` |

Each marker carries the session's organization, email, account and session ID (the session it was made in, even where a `/clear` ended it while the marker was being made), the tool call that made it (`gen_ai.tool.call.id`), the span it was made in (`mainwave.caller.trace_id`, `mainwave.caller.span_id`; none on the snapshot, made before its prompt's interaction begins), the subagent (`mainwave.subagent.id`) and the prompt (`prompt.id`, on the snapshot and the failure, where Claude Code says which), in a trace of its own, as the CLI's do: Mainwave keys a marker's run on its trace. Its resource is the session's, with the CLI marker's `mainwave.source`, `service.name`, `mainwave.host_source` (`coding_agent.claude_code`) and `mainwave.schema.version` over it. Like the plugin's own rows, a marker waits for a row of Claude Code's to say who the session is, or, where no row reaches the plugin, for the host's variables or the account file to say it (see `rows_skipped`, below).

- **Only where its key goes.** A commit, pull request or ticket marker is sent only while the data point of its key is on, and nothing runs to make one while it is off: without its key Mainwave could neither count it nor join it. With no settings that is none of them (their keys are identifiers); the snapshot and the failure go. Every other attribute follows its own data point (a commit's paths `file.path`, a title `change.title`), and the protections and packs, as any record does. Claude Code sends no marker, so a data point set to as Claude Code sends it sends none of a marker's values.
- **Beside the CLI's hooks, one copy.** Where the merged settings run the CLI's hook for a marker (`mainwave-hook.sh claude-code <Event> <route>`), the script it runs is on the machine (the managed command does nothing where the CLI was never installed), and the session gives the CLI a key to send with (`OTEL_EXPORTER_OTLP_ENDPOINT`, and an `Authorization` header in `OTEL_EXPORTER_OTLP_HEADERS` or an `otelHeadersHelper`), the CLI sends that marker and the plugin does not, so nothing counts twice. The plugin reads those variables only to see whether a key is there; it never keeps or sends the key. Where the hooks run but there is no key (an organization took its env block out), the CLI's hooks send nothing, and the plugin's markers stand in.
- **Where it can.** The lookups (`git`, `gh`, `glab`) run on the host, so in Cowork, which runs no host commands, a commit makes no marker and a pull request goes without its size. A lookup gets 5 seconds at most (2.5 for glab), beside the call: it never holds the call up. The kind of a turn's API error is read from the end of the session's transcript (its last 64 KiB, then further back, up to 4 MiB, a few times over half a second while the line is not found), so a session that keeps no transcript sends no failure marker; nor do Claude Code versions without `$.session.info` (2.1.325 and earlier, the floor among them), which also give no prompt ID for the snapshot. The session's end waits half a second at most for markers still being made.
- **Keyless ingest has to keep them.** The collector strips every `mainwave.*` key a keyless request carries but the plugin's own stamps, and the markers' source with them; it keeps them once it lets keyless markers keep their `hook.*` source and keys.

**It says what's wrong with the telemetry setup.** As the session's first turn ends, the plugin sends one row of its own, `plugin_status`, through its copy, and another only when what it says changes (10 at most per session, counted from when the plugin loads; a new session after `/clear` has its own). The row carries the session's identity, the plugin's stamps and `mainwave.telemetry.issues`: the codes of what it found, from the fixed list below, in that order. A row with nothing wrong carries no list. Mainwave shows the organization each code with what fixes it.

| Code | When |
| --- | --- |
| `rows_skipped` | No row of Claude Code's reached the plugin since it loaded, 5 seconds after its first model request ended (or as the session ends): every model request raises one. A turn that asks no model counts for nothing. So the session ran on rows the plugin built from Claude Code's events (Two modes, above). That is the expected mode for an org-synced plugin in Team and Enterprise organizations from Claude Code 2.1.328 on, in Claude Code and Cowork alike, and nothing needs fixing. The exporter's codes need telemetry on. Of a headers variable the plugin reads whether a header is named `Authorization`, never a value, and the row carries the codes alone: no endpoint, host, header or command. What it can't report: a collector that refuses the copy refuses this row too; a `collectorUrl` sends it where it sends the copy; a Claude Code below the plugin's floor never loads it; and where no row reaches the plugin, a session whose host names no organization and email, and whose account file holds no login or that signs in another way (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, a token a host hands in as `CLAUDE_CODE_OAUTH_TOKEN` or `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, a token or key on a file descriptor, a gateway's token, Bedrock, Vertex or Foundry, an `apiKeyHelper`), has no identity to send it under, as the account file's login may then not be its own. The session-end debug line lists the codes too.

Rules it keeps:

- **It never holds anything up.** The exporter's row always goes on, whether or not the copy could be queued. If stamping fails, the row goes on as Claude Code wrote it, minus any key the plugin owns. The hooks on turns, model requests, tool calls, slash commands, subagents, prompts and skill prompts only watch: each passes its event and its result on unchanged, and a fault in one is caught.
- **Nothing else can pose as it.** Any key under `mainwave.plugin.`, `mainwave.telemetry.`, `mainwave.redaction.` or `mainwave.command.` already on a row is removed before the plugin adds its own. So is any key under `mainwave.mod.`, where earlier Mainwave plugins put their stamps. Each value it adds must fit a fixed shape.
- **It sends to one place.** The copy goes to Mainwave's production collector, or to the collector the person's own user settings name, and sends no key. The plugin never reads the organization's collector URL or key, and no repository, `--settings` or managed setting can send the copy elsewhere. This holds against settings, not against other plugins: any plugin the person installs can see and rewrite every plugin's requests, this one's included.
- **It sends what its data points allow, and nothing else.** What each data point is, and when it goes, is in What it sends, below. It adds no commands, panes or tools.

With no collector configured, the plugin has no rows to stamp, but it still sends its keyless copy. A session whose rows name no organization and email (an API key, a cloud provider) sends nothing, and asks Mainwave nothing.

## What it sends

Everything the plugin sends belongs to one data point, named by an ID. Four are required: Mainwave can't route a record, join records or count spend without them, so they have no setting. Each of the others is on, off, or as Claude Code sends it:

- **On:** the plugin sends it, adding what it read in its own hooks where Claude Code's row or span leaves it out.
- **Off:** the plugin sends it in none of its records, its copies of Claude Code's rows included (prompts and responses read `<REDACTED>`, as Claude Code writes withheld text).
- **As Claude Code sends it:** the plugin sends it exactly where Claude Code's own telemetry does under the session's settings, and nowhere more.

These settings govern what the plugin sends. Where an organization's env block is in place, Claude Code's own exporter goes on sending its rows, spans and metrics under Claude Code's switches; the plugin only stamps the exporter's rows and cannot change what that exporter sends. The Default column is the plugin's own default, with no organization settings; with the organization's settings in force, what they give in force replaces it (see Defaults, below). A setting named in the Default column is the Claude Code switch that governs the data point.

**Defaults.** With no settings, the plugin sends the required and metadata data points only, in Claude Code and Cowork alike. Identifiers and content are off until the organization's settings turn them on. Once the organization's settings from Mainwave are in force, its defaults are those its settings page shows instead (The organization's settings, below). Claude Code's switches don't turn a data point on: where `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT`, `OTEL_LOG_USER_PROMPTS` or `OTEL_METRICS_INCLUDE_REPOSITORY` is set, Claude Code's own exporter sends what it says, and the plugin's copy still leaves identifiers and content out (prompts and responses read `<REDACTED>`) unless the organization's settings, what they give in force included, turn them on. A switch the session's environment sets to `0` (or `false`, `no`, `off`) turns the data points it governs that are on by default (the metadata `tool.mcp`, `skill.name`, `agent.type` and `web.domain`; with the organization's settings in force, also each identifier and content data point it governs that the organization left at a default of on) to as Claude Code sends it, which with that switch off is little or nothing: Mainwave's org-wide setup writes `0` for a capture an admin turns off, and the plugin keeps that choice. Where a data point is on and Claude Code's row leaves its value out (Cowork's export carries no tool details, content or prompts), the plugin adds what it read in its own hooks: the call's parameters and input, the prompt, the response. A person can opt in, for their own sessions, to a data point that is off by default (see Settings): it turns on unless such a switch governs it. An explicit setting for a data point wins over all of these: the data points the organization set itself on Mainwave's settings page (below) are explicit settings. So, in order: an explicit setting, then a switch at `0`, then the person's opt-in, then the default (the organization's in force, else the plugin's). An organization that sets a data point on itself sends it even where a switch is at `0` (one only on in force does not), and one that sets it off keeps it off even where the person opted in.

**The organization's settings.** The plugin asks Mainwave for them once a row of Claude Code's names the session's organization and email, which a session on a claude.ai login does from its first rows:

- **What it sends.** A POST to `https://api.mainwave.com/api/plugin/data-collection-settings`, Mainwave's API beside the collector its copy goes to (the dev API where the person's `collectorUrl` names Mainwave's dev collector, and that collector itself for any other), with `{"claude_org_id": "<organization>", "email": "<email>"}` as its body and nothing else: no key, no account or device ID, no record. The email goes in the body so no request log keeps it. The person's user settings are read again before each request, so it goes to the Mainwave the copy goes to; while they can't be read, nothing is asked until they can, and where they name a collector of the wrong shape, or a repository's settings name `collectorUrl`, nothing is asked until the plugin loads again. Mainwave answers only for an organization and email its keyless ingest would route, and refuses the rest as keyless ingest does.
- **What it does with the answer.** The plugin sends what the organization's settings page shows. The data points the organization set itself (`data_points`, `on` or `off`) become the explicit settings. Every other data point takes the value the answer gives it in force (`in_force`: what the page shows, Mainwave's defaults for those the organization left alone) as its default, in place of the plugin's, and the rest of the rules above still apply to it: a switch at `0` keeps one on in force as Claude Code sends it, and the person's opt-in raises one off. So an organization that never changed a setting gets every data point Mainwave's page shows on, identifiers and content included. A data point the answer doesn't name in force (one Mainwave's catalog doesn't have yet), and every data point where the answer has no `in_force` (an older Mainwave's), keeps the plugin's default. Its redaction packs (`redaction_packs`) run, with those of the organization's managed settings and the person's added (see Redaction packs, under Settings). The answer applies at once, to records already queued as they are sent: a data point turned off leaves them, and one turned on goes on what is captured after it. The plugin keeps the answer in its store, whole and in one write, under `dataCollectionSettings` with the organization it is for (`in_force` as `inForce`), so the next session of that organization starts from it. An answer an earlier version kept, without `inForce`, applies its explicit settings alone until Mainwave answers again.
- **When.** At once when a row first names the organization and email, then every 4 minutes while the session runs, and again as a later session starts in the same process (after a resume, say). While the person's user settings can't be read, it tries again every 30 seconds. The request goes from a timer, never from a hook, so it never holds up a row, a turn or a tool call.
- **Until it answers.** The settings the store keeps for the session's organization apply; those kept for another organization never do. With none kept, the defaults: required and metadata data points only, and the packs of the organization's managed settings, else `secrets` alone. Where the store keeps nothing for the organization, identifiers and content it turns on start with the records captured after its first answer, so a session's first rows may go without them.
- **When it fails.** No network, a timeout, or a server error: the settings in force stay, and the plugin asks again after 30 seconds, then 60, and so on up to 4 minutes. A refusal (403 `unclaimed` or `email_domain`, a malformed email, the organization's request budget spent, or a 404 where Mainwave's route is off): the settings in force stay, and it asks again 4 minutes later, or after the `Retry-After` of a 429 where that is longer (up to an hour). None is shown to the person; the end-of-session line in the debug log says where the settings came from and how the last request went, never the email. An answer of the wrong shape changes nothing. Packs the answer names that this version doesn't have hold identifier and content values back, as for managed settings.
- **No organization, no email.** A session whose rows name no organization and email asks nothing, and the settings the store keeps for an organization don't apply to it.
- **A store that can't be read** applies none of the organization's settings, and holds identifier and content values back, as the packs chosen are not known.

The store is a file on the person's machine. Settings written in it by hand, under `dataPoints` and `redactionPacks`, apply to every session while it keeps no answer from Mainwave: a convenience, not a control.

**The plugin's own rows.** `mcp.url` and `skill.text` are on no row of Claude Code's, so the plugin sends rows of its own for them, with the session's identity and stamps, once a row of Claude Code's has said who the session is. After a `/clear` or a resume, the session that follows gets its own: its servers and skill texts are sent again under its ID.

- For `mcp.url`, at session start, the plugin reads the MCP server entries Claude keeps:
  - `mcpServers` in Claude Code's global config (`.claude.json` in `CLAUDE_CONFIG_DIR`, else the home folder), for the user and for the project;
  - `.mcp.json` in the project folder and each folder above it, the servers Claude Code would load alone (approved, and not refused, as the settings and the project's entry in the global config say);
  - the managed `managed-mcp.json`, in the managed settings folder of the session's OS; where present, it is the only file read, as only its servers load;
  - the `.mcp.json` and manifest of each plugin installed and enabled;
  - outside the CLI, Claude Desktop's `claude_desktop_config.json`.

  It takes each server's name, transport and address, and never its headers, environment or anything else in those files. A server the organization's `deniedMcpServers` names is not sent, nor, where its `allowedMcpServers` lists servers by name, one it doesn't list. In a local server's command, the value after a flag that names a secret (`--api-key`, `--authorization`, `--cookie`), a header (`-H`) or an environment variable (`-e`) is replaced before the always-on protections run. A remote server's path is kept as written, so a token a service puts in its path goes with it; an address whose password can't be told from its host sends its scheme alone. A server in none of those files (a claude.ai connector, one the host app provides, one set on the command line) gets its row when a call first names it, with the name its tools are called by and the scope Claude Code's row gives.
- For `skill.text`, the plugin reads the text the engine expands for the model; a later run of the same text in the session carries only its `skill.text_id`. A run counts as given arguments when its slash command or Skill call had any, or when its text holds them, and its text then goes only where `prompt.text` does.

**What a shell command did.** Mainwave counts commits, pushes, branches and pull requests from the shell commands a session runs. Where it has a command's text (`bash.command`), it reads them from the text; where it does not, it reads what the plugin stamps on the command's `claude_code.tool` span, so the counts need only `bash.outcome`, and the text can stay on the machine. The plugin reads each command, in Bash or an MCP shell tool, by Mainwave's own rules: only a command position counts (the start, or past `&&`, `;`, `|` or a newline), so a commit message or an `echo` that mentions `git push` counts nothing. Neither does the body of a heredoc whose tag is an upper-case word (capitals, digits and `_`, as in `<<EOF` or `<<'SQL'`), up to its first line that is `EOF` (for `<<EOF`) or a bare upper-case word. Where Mainwave's rules read a command otherwise than the shell does, the plugin counts as the rules do. Among those cases: a separator escaped with a backslash inside a quoted string, as in `git commit -m "a\; git push"`, where the rules read a command position; the body of a heredoc whose tag has a lower-case letter (`<<msg`, `<<'Msg'`) or that has no terminator line, which the rules read as commands; and an ANSI-C string (`$'…'`), which the rules end at its first quote, even an escaped one (`\'`). A ref (the branch, ref or tag beside a count) is read only from a counted invocation that no escaped separator starts; none is read past a `<<` the rules leave in place, as those heredocs' openers are, or past one whose body the shell may read otherwise: its tag is a longer word to the shell or has unpaired quotes, its opener's line opens a quote it does not close on that line, or the line the rules end its body at is not exactly its tag (after leading tabs, for `<<-`). Nor is one read from a command holding an ANSI-C string with an escaped quote. The plugin splits its words as the shell does: quotes, backslash escapes, `$(…)` and backticks keep a word whole, and a quoted string the rules cut for holding a separator or a newline still closes where the shell closes it. It reads them from the subcommand to the end of its simple command (an unquoted newline, `&`, `|`, `;` or `)`, but for the `&` or `|` of a redirect such as `2>&1`), and skips each flag that takes a value, together with its value, and each redirect, together with its target. The ref is the word Mainwave's rules name: for a push, the word after the remote; for a tag, the word after `tag`, `tag -a` or `tag -s`; for a merge, its first word that is not a flag; for a new branch, the value of `-b`, `-B`, `-c`, `-C`, `--create` or `--force-create`. The plugin sends that word only when it has a git ref's shape: at most 256 characters, not starting with `-`, of letters, digits, `.`, `_`, `-`, `/`, `@`, `+`, `:`, `,`, `=`, `%`, `#`, braces and `$` before a variable's name, bare or wrapped whole in one pair of quotes (kept, except on a new branch's name). Otherwise it sends no ref, and still sends the count. Where the text is sent, Mainwave reads refs more widely, and may name one where the plugin names none or another. `tests/fixtures/command-outcomes.json` is a copy of the cases Mainwave's rules pass, and the plugin's tests run every one. Every shell command's span carries `mainwave.command.counted`; only one that ran and succeeded carries counts, while the text, where it is sent, counts every command run. A ref longer than the attribute limit is left off rather than cut. Claude Code sends none of these keys, so a data point set to as Claude Code sends it sends none of them.

**When it is decided.** As a record is captured, and again as it is sent, so a record queued before a data point was turned off goes without it. A record an earlier session left in the outbox went through that session's settings, which this one doesn't know, so a data point set to as Claude Code sends it goes on that record only if it is on.

**What Claude Code withholds whatever its switches say,** the plugin withholds too where it can see it: an account-memory tool's (`mcp__memory__memory_*`) input and output are recorded only as their length, and responses to Claude Code's memory operations and other requests outside the conversation are not filled in. Claude Code also takes account-memory text out of the prompts and responses it records; the plugin can't see the account's memory, so a prompt or response it fills in keeps such text.

**Always on.** Whatever the settings, every identifier and content value but the session's identity is cleaned on the machine before it is queued:

- Secrets are replaced with a marker naming their kind (`[REDACTED:github_token]`): AWS access key IDs, GitHub tokens, Anthropic and OpenAI-style API keys, Slack tokens, private key blocks, JSON Web Tokens, `Authorization` header values, passwords in web addresses (`https://user:pass@host`), and values assigned to names containing `password`, `secret`, `token`, `api_key`, `access_key` or `private_key`. A record that had any carries their count, `mainwave.redaction.count`.
- Long values are cut at 61,440 characters, Claude Code's own limit for telemetry content, or at what `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH` sets; lower where `OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT`, `OTEL_SPAN_ATTRIBUTE_VALUE_LENGTH_LIMIT` or `OTEL_LOGRECORD_ATTRIBUTE_VALUE_LENGTH_LIMIT` says. A cut value ends with Claude Code's `[TRUNCATED` marker and carries `<attribute>_truncated` and `<attribute>_original_length`.

**Redaction packs.** Beside the secrets, the plugin runs the personal-data packs the organization chooses, the same packs, rule names and matches as Mainwave's SDKs and CLI hooks (one difference: the secret rules always run first here, so a card number inside an API key is replaced as the key):

| Pack | What it replaces |
| --- | --- |
| `secrets` | The secrets above. Always on |
| `pii.contact` | Email addresses (`[REDACTED:pii.contact.email]`), North American phone numbers (`pii.contact.phone_nanp`) and international numbers written with a `+` (`pii.contact.phone_e164`) |
| `pii.us_gov_id` | US Social Security numbers written with dashes, such as 123-45-6789 (`pii.us_gov_id.ssn`) |
| `pii.payment_card` | Card numbers that pass the Luhn check, with or without separators (`pii.payment_card.card_number`, `pii.payment_card.card_number_grouped_19`) |

With no choice from the organization, `secrets` runs alone, as Mainwave's org-wide setup applies to its hooks by default. A pack that is on runs on every identifier and content value the plugin sends, the same ones as the secrets: prompts, responses, thinking, tool input and output, shell commands (an MCP shell tool's such as `device_bash` included), file paths, web addresses, MCP server addresses, skill text, and error and status messages, in Claude Code and Cowork alike. Each match is replaced with `[REDACTED:<pack>.<rule>]`, after the secrets, and counts in `mainwave.redaction.count`. A value that is JSON (a call's `tool_parameters`, for one) is scanned value by value and keeps its shape: keys aren't scanned, and a number that matches becomes the marker as a string. JSON that no longer parses, as when it was cut at the limit, is scanned as text and again between its escapes, so a number after a `\n` is still found. The resource's values are scanned too, as `OTEL_RESOURCE_ATTRIBUTES` can hold anything. The keys that say who sent a record and that Mainwave routes and joins on (`organization.id`, `user.email`, `user.account_uuid`, `session.id`, `prompt.id`, a repository's address, a commit and the rest of the list Mainwave's SDKs share) are never scanned by a pack. If the packs chosen can't be read or name a pack this version doesn't have, the plugin sends no identifier or content value at all (except those keys), rather than send what it couldn't check; the records still go, and the session's debug log says why. See Settings for how a pack is chosen. Like the rest of this section, the packs apply to the plugin's copy: Claude Code's exporter sends its rows to the organization's collector as Claude Code writes them.

## What is coming

In rough order, each in a later version:

1. **A setup that sends less, reported.** The plugin tells Mainwave when the session's configuration keeps it from sending everything: no rows reach it, the CLI's hooks run with no key, the organization's settings can't be fetched, and the like.
2. **The session's state from Mainwave.** The plugin already asks for the organization's data points and redaction packs. Next it asks for the session's state too (whether Mainwave accepts this computer and person), by the organization, account, email and device it read.
3. **Attributes.** The organization's attribute list in the session: Claude or the person sets a value (such as the project) with `/mainwave:attribute`, or proposes a new one for an admin to accept.

## Install

Needs Claude Code 2.1.317 or later.

`claude --version` shows the version, and `claude update` updates a native install. Other installs update through their package manager: `brew upgrade claude-code`, `winget upgrade Anthropic.ClaudeCode`, `sudo apt update && sudo apt upgrade claude-code` (dnf and apk alike) or `npm install -g @anthropic-ai/claude-code@latest`. Homebrew, WinGet and Linux package installs do not update by themselves by default.

On an older version the session is unaffected, as the plugin fails open, but the plugin sends less or nothing:

- Below 2.1.299, its hooks module does not load, so it stamps and sends nothing.
- From 2.1.299 to 2.1.316, its copy's spans lack `gen_ai.provider.name`, and on early versions of that range its keyless copy has gaps too (rows that name the wrong parent span, subagents' requests missing).
- From 2.1.317 to 2.1.325, which give a plugin no `$.session.info`, it sends no `mainwave.claude_code.stop_failure` marker, and the plan snapshot carries no `prompt.id`.

The version that counts is the one each session runs, and a person who has updated Claude Code in their terminal may still run older copies elsewhere:

- **Remote machines.** A session over SSH, or in a container or VM, runs the Claude Code on that machine, not the local one: update it there. The desktop app's SSH sessions are the exception: they run a copy the app installs on that machine, not its `claude`.
- **Scripts and CI.** A `claude -p` run uses the binary its job installs, often a pinned version. Raise the pin.
- **IDE extensions.** The VS Code extension runs the copy of Claude Code it bundles, and its version number is that copy's: update the extension. If its `claudeProcessWrapper` setting names another `claude`, that one runs instead: update it. The JetBrains plugin runs the `claude` on the machine's `PATH`, or the one its settings name: update that.
- **The desktop app.** In a local session, its Code tab runs its own copy of Claude Code, which the app downloads and updates, so it can differ from the terminal's `claude`, and updating one does not update the other. `/status` in a session there shows its version. Update the app (**Claude › Check for Updates…** on macOS, **Help › Check for Updates…** on Windows), then start a new session.

An organization can turn older versions away: the managed setting `requiredMinimumVersion`, set to the floor, makes Claude Code below it exit at startup (it is read from Claude Code 2.1.163 on).

`plugin.json` states the floor too, as `engines`. Claude Code reads `engines` only from 2.1.323 on, so today it turns no version away: every version that reads it is above the floor.

### For a whole organization (org sync)

An owner or admin of the Claude organization, on claude.ai:

1. **Organization settings › Plugins & skills › Sync from GitHub**, then add `mainwaveai/mainwave-agent-plugin` with **Sync automatically** on. While the repository is private, Anthropic's GitHub app must be able to read it.
2. **Inventory › mainwave › Default access › Required**, so every member's Claude Code and Cowork sessions run it with no install step.
3. If an older Mainwave plugin is in the inventory, set it to **Not available**, so only one copy stamps rows.
That is all the plugin needs; each re-sync picks up the repository's `main` branch. In Team and Enterprise organizations, Claude Code 2.1.328 and later keep Claude Code's rows from an org-synced plugin, so it builds them from Claude Code's events (Two modes, under What it sends).

Don't also add this repository to the organization's managed settings (`extraKnownMarketplaces`, with `enabledPlugins` naming `mainwave@mainwave`). On 2.1.328 it does not bring the rows back: Claude Code seats a plugin from a remote-source marketplace in the organization's tier only once it records a hash of the plugin's copy, which it does not yet, so the plugin stays in the `user` tier. It does harm. It locks out the org-synced copy, and it pins the marketplace's copy in each machine's plugin cache at the version it first installed, which updates only when the version changes.

Where rows do reach the plugin (a personal account, Claude Code before 2.1.328), its stamps on Claude Code's own exporter rows also need Mainwave's managed `env` block (from Mainwave's org-wide setup). Without it there is nothing of Claude Code's for them to go on. The plugin's copy goes either way.

To check it works: run a session, then look for rows with `mainwave.plugin.name = mainwave` in Mainwave. The session's `plugin_status` row says which mode it ran in: `rows_skipped` where it built the rows.

### For yourself

At the prompt of a Claude Code session in a terminal:

```text
/plugin install mainwave --marketplace mainwaveai/mainwave-agent-plugin
```

Answer `y` to add the marketplace, then pick a scope. From a shell: `claude plugin install mainwave --marketplace mainwaveai/mainwave-agent-plugin`. While the repository is private, your machine needs a git credential for github.com that can read it.

## Settings

The plugin reads three settings: where the copy goes and the data points the person opts in to, both the person's own and read from their user settings alone (`settings.json` in `~/.claude`, or in `CLAUDE_CONFIG_DIR` where that is set), and the redaction packs, which the organization chooses and the person may add to. None can come from a repository's settings, and the person's two can't come from `--settings` or managed settings either. There is no switch to turn stamping or the copy off; to stop the plugin, remove it.

### Collector

`collectorUrl` sends the copy to another collector than Mainwave's production one: Mainwave's dev collector for Mainwave's own testing, or a local receiver. Unset (the default), the copy goes to `https://collector.mainwave.com`.

```json
{
  "pluginConfigs": {
    "mainwave@synced": { "options": { "collectorUrl": "https://collector.dev.mainwave.com" } }
  }
}
```

The name to use is the plugin's ID: `mainwave@synced` for org sync, `mainwave@mainwave` for an install from this repository, or `mainwave` (or `mainwave@inline`) for a `--plugin-dir` load.

- **Its shape.** The collector's base URL, as `OTEL_EXPORTER_OTLP_ENDPOINT` takes it: an `https` URL, or `http` on `localhost`, `127.0.0.1` or `[::1]`, with no user, password, query or fragment. A path is kept, and the signal's `/v1/logs`, `/v1/traces` or `/v1/metrics` goes after it, so leave those off. A value of any other shape, or plugin IDs that name different collectors, send nothing and drop what was queued until the plugin loads again (the session's debug log says so, never with the value): the person meant the copy to go somewhere else, so it goes nowhere rather than to production.
- **Keyless there too.** The copy goes without a key wherever it goes; the collector routes it by the organization and email on each record.
- **Read before each send.** A change from one collector to another takes effect from the next batch. User settings that can't be read hold the copy back, its queue kept, until they can: they may name another collector. An outbox an earlier session left goes to the collector the session that sends it names.
- **Only your user settings count.** If a repository's settings (`.claude/settings.json` or `.claude/settings.local.json`) name `collectorUrl` under any of the plugin's IDs, to any value, or cannot be read, the plugin sends nothing and drops what it had queued.

`collectorUrl` is not declared as a plugin option, so `/config` doesn't show it, for the same reason as `extraDataPoints` (below). Earlier versions' `devIngestKey` and `devKeyless` options are gone: a value left in settings or secure storage is ignored, and the copy goes keyless to production.

### More data points, for your own sessions

`extraDataPoints` lists data points for the plugin to send from your own sessions where they are at a default of off (the plugin's, and, with the organization's settings in force, Mainwave's too): any identifier or content data point (see What it sends), such as `prompt.text`, `repo` or `response.thinking`. Put it in your user settings, under the plugin's ID as above:

```json
{
  "pluginConfigs": {
    "mainwave@synced": { "options": { "extraDataPoints": ["response.thinking", "mcp.url"] } }
  }
}
```

The value is a list of IDs, or one string of IDs separated by commas or spaces. The limits:

- **It only adds.** Each listed data point that is at its default of off turns on. Listing one that is already on changes nothing, and nothing in the list turns anything off.
- **An explicit setting wins.** A data point an admin or the organization set to off stays off, whatever you list. So does one a switch the session's environment sets to `0` governs: Mainwave's org-wide setup writes `0` when an admin turns a capture off. Thinking is the model's output, so for this it follows the responses' switch: with `OTEL_LOG_ASSISTANT_RESPONSES` (else `OTEL_LOG_USER_PROMPTS`) at `0`, listing `response.thinking` sends no thinking.
- **The nesting rules hold.** `mcp.url` goes only where `tool.mcp` does, and `skill.text` only where `skill.name` does (a skill's text with arguments, only where `prompt.text` does too). Both of those follow `OTEL_LOG_TOOL_DETAILS`, so with that set to `0` neither goes anywhere. `tool.input` holds commands, file paths and web addresses, so it goes only with `bash.command`, `file.path` and `web.url` listed too.
- **Only your user settings count.** The plugin reads the list from them alone. A repository's settings (`.claude/settings.json`, `.claude/settings.local.json`), `--settings` and managed settings are ignored, so a repository can never raise what the plugin sends.
- **A mistake is ignored.** Unknown IDs, required data points and values of another type are ignored, and the plugin goes on as without them. User settings that can't be read opt in to nothing.
- **Read again before each send.** The plugin reads the list when it loads and again before each batch it sends, so a data point you take off the list stops going out, from records already queued too. One you add starts by the next session at the latest: the MCP servers are read as a session starts.
- **Mainwave can see it.** Every log row and span the plugin sends while your list turns something on carries `mainwave.telemetry.opt_in`, listing those data points (`mcp.url,response.thinking`), so an admin can tell why that data is there. A data point the rules above keep from going anywhere is not listed. It changes only the plugin's copy: Claude Code's exporter sends what its switches say, and its rows carry no such stamp.

`extraDataPoints` is not declared as a plugin option, so `/config` doesn't show it and `claude plugin configure` doesn't set it: Claude Code refuses to load a plugin whose declared option holds a value of the wrong type, and a mistake here must never stop the plugin.

### Redaction packs

`redactionPacks` lists the redaction packs to run (see What it sends): `pii.contact`, `pii.us_gov_id`, `pii.payment_card`, and `secrets`, which always runs. An admin sets it for the whole organization in its managed settings, the ones Claude Code reads for every member wherever they come from, under the plugin's ID:

```json
{
  "pluginConfigs": {
    "mainwave@synced": { "options": { "redactionPacks": ["pii.contact", "pii.us_gov_id", "pii.payment_card"] } }
  }
}
```

The value is a list of pack names, or one string of names separated by commas or spaces. The rules:

- **The organization's choice replaces the default.** Its packs in Mainwave's data collection settings (see The organization's settings) and those of its managed settings both run: a pack named in either runs. With neither, `secrets` runs alone. There is no managed setting for data points: those come from Mainwave alone.
- **A person can add packs, never remove one.** The same option in a person's user settings (`settings.json` in `~/.claude`, or in `CLAUDE_CONFIG_DIR`) adds its packs to the organization's for their own sessions. Nothing in it turns off a pack the organization's list or the default turns on.
- **Only managed settings and the person's user settings count.** A repository's settings (`.claude/settings.json`, `.claude/settings.local.json`) and `--settings` are ignored.
- **A mistake holds content back.** Unlike the opt-in, where a mistake is ignored, a pack name this version doesn't have, a value of another type, or managed or user settings that can't be read make the plugin send no identifier or content value (see What it sends). Redaction that was asked for never silently turns off.
- **Read again before each send,** as the opt-in is, with the organization's data collection settings as the plugin last had them: a pack added mid-session applies to records already queued.

`redactionPacks` is not declared as a plugin option either, for the same reason as `extraDataPoints`.

## Developing

The plugin sits at the repository's root: `.claude-plugin/plugin.json` (the manifest), `.claude-plugin/marketplace.json` (this repository as a marketplace), `hooks/` (the hooks module, `register.ts`, and the modules it imports), `types/index.d.ts` (what it keeps in `$.state`) and `tests/`.

```sh
claude plugin validate .        # reads the manifest, the marketplace and the hooks module the way Claude Code will
claude plugin test .            # runs tests/*.test.ts against the engine
scripts/check-version.sh        # plugin.json and hooks/version.ts agree; the Claude Code floor is the same in CI's pin, plugin.json and here
scripts/check-layout.sh         # one plugin, at the root: org sync refuses a .claude-plugin/ or plugin.json anywhere else
scripts/check-hooks.sh          # the row, tool call, command, prompt and spawn hooks keep their fail-open .catch; the turn hooks, tool.check, session.measure and session.end are hooked; no classic hook
scripts/check-vendored.sh       # the copies of Mainwave's catalog and command cases (JSON) and the twins the tests import agree; --write rewrites the twins
node tests/e2e/compare.mjs      # real sessions, model mocked: the plugin's copy against the exporter's; without the env block, keyless and coherent
MW_E2E_SEATED=1 node tests/e2e/seated.mjs   # with managed settings on the machine: the marker hooks run past Claude Code's security default
claude --plugin-dir .           # a session with the plugin loaded from this folder
```

CI runs all but the last on every pull request, on two Claude Code versions: the latest, pinned in `.github/claude-code/package.json`, and the floor, the oldest version the plugin supports, pinned in `.github/claude-code-floor/package.json`. Dependabot opens a pull request for each new Claude Code release, so a release that breaks the comparison fails that pull request alone. Dependabot's version updates don't watch the floor, so it changes only by hand: raising it is a pull request of its own, which changes the pin, `engines` in `plugin.json`, the Install section and the note at the README's top together (`scripts/check-version.sh` fails where they differ). To run the checks on another version, install it in a scratch folder (`npm i @anthropic-ai/claude-code@<version>`) and put it first on `PATH`, with `DISABLE_AUTOUPDATER=1`.

The end-to-end comparison runs `claude -p` in a fresh config folder and a scratch git repository, with an API key and a local mock of the Anthropic API, so no login and no organization's settings reach it but the explicit ones below, and nothing leaves the machine. The mock model scripts a turn that runs Bash, writes and edits a file, commits, has a command fail, is refused a command and starts a background subagent; it answers each request after a different delay, and refuses one request once as overloaded, so Claude Code retries it. The session runs four times: with the env block, once with Mainwave's org-wide setup captures on and once with each set to `0`; then without it; and once more with it, as no row reaches the plugin. With the env block, the plugin's store holds explicit settings that turn on the identifiers and content those captures govern (on, then as Claude Code sends them), as an organization's settings would, so the copy has them to compare. With it, Claude Code's exporter sends all three signals to a local receiver, and the person's user settings name that receiver as the plugin's `collectorUrl`, so the copy goes there too. The script pairs every log row by session, event name and sequence; every span by what identifies it (its ID where the rows name it, else its request ID or tool call ID); and every metric series by its name and attributes, summing its points. It compares each pair field by field, attribute keys in order and value types included, and fails on any difference but the known ones in the table above, which it lists with their counts. The plugin's markers have no counterpart and are checked apart: with the captures on, the session's commit goes as one `vcs.commit.created` marker, named as the repository's HEAD names it, under `hook.git`, naming the call that made it, in a trace of its own; with them as Claude Code sends them, and without the env block, none goes (the repository is off), and no other marker goes in any pass but the fifth. The first runs in auto mode: the mock answers auto mode's classifier, blocking the refused command and allowing the rest, and it counts the exporter's spans of the classifier's requests as the known gap above, and, where the exporter counts those requests in `cost.usage` and `token.usage` (as through the mock, which stands where a gateway would), that share too, each token type's exactly the tokens on those spans; it fails unless the classifier was asked about that command and refused it. Without the env block, the exporter sends nothing and the plugin, with no settings, sends to Mainwave's production collector: a test-only plugin, built in a temporary folder from `tests/e2e/redirect.ts`, sends those requests to the receiver on a path of their own (and refuses any to the dev collector), so the script fails on any copy that went elsewhere than production, or, with the env block, elsewhere than the receiver the settings name. In every pass the receiver applies keyless ingest's rules to the copy (no `Authorization` header; an `idempotency-key` header of the collector's shape, which the plugin sends on every request; one `organization.id` and one `user.email` on every item, the same pair across a request) and the script fails on any request it refuses. Without the env block it also fails on any span out of its place in the interaction's trace, on any row that names a kind of span other than the exporter's rows of the same event named with the env block, when the copy lacks the metadata its defaults send (a command's class, a subagent's type, a failed call's error class), and when it carries any identifier or content its defaults leave out (a command, a file path, tool input or output, a repository, a prompt or a response). Without the env block the plugin also asks for its organization's settings on production's API: the test-only plugin sends that request to the receiver too, which answers as Mainwave's settings API would, turning a metadata data point off (`file.kind`) and adding a pack, with an `in_force` that names that data point alone (so the rest keep the plugin's defaults, and the pass can check the copy carries no identifier or content; the unit tests cover an answer with every data point in force), and the script fails unless the request carried the organization and email alone, the store kept the answer with its organization and what it gave in force, and no `code_edit_tool.decision` point carries a language. With the env block the plugin asks the receiver the settings name, which answers as the route off, so the explicit settings in the store stand. In that last pass a test-only plugin, built from `tests/e2e/skip.ts` and loaded ahead of the plugin, keeps every row of Claude Code's and the session's identity from it, as the built-in plugin of Team and Enterprise organizations does (an API key's session never seats that one). A plugin can't send a row on past the plugins after it as that one does, so it takes each row itself, and the exporter gets none either. As in the other passes, the session's organization and email reach the rows through `OTEL_RESOURCE_ATTRIBUTES`, which the built rows start with as Claude Code's do: on an API key, the plugin names no one itself. The script fails unless every row the plugin sends is built from events and none is a copy, and its status row says `rows_skipped`. Its rows must count what the exporter's rows of the same scripted session count (the second pass's): as many prompts, the main loop's and subagents' requests with their tokens to the token and their cost within a thousandth, and a result for each call that ran. The token and cost metrics must match this session's exporter's. Its spans must make one coherent trace per interaction, as many interactions and requests as the exporter's. The pass turns on the content Cowork's export leaves out (`prompt.text`, `response.text`, and `tool.input` with what it holds), as an organization's settings would. The script fails unless each built prompt row carries the prompt's text, each response row its response's text, as many as Claude Code logs, and each result row its call's input. Last, it compares the plugin's copy in the second pass, made from Claude Code's rows, with the rowless pass's built copy, field by field. Each built row is paired with its counterpart by call, request or order. The script fails on any field the built copy lacks that the README's What Claude Code's rows add does not list, on any field the two give different values (ids, times, sizes and the session's own paths aside), and on any metric whose sums differ. It prints the fields Claude Code's rows add. As the sessions run on an API key, their rows carry an organization and an email only through `OTEL_RESOURCE_ATTRIBUTES`, standing in for what a login puts on them. A fifth session, also without the env block, sends a prompt the mock refuses as rate limited, with Claude Code's retries off, so its turn ends on an API error: from 2.1.326 the plugin must send one `mainwave.claude_code.stop_failure` marker, keyless, under the session's identity and in its session, carrying the kind the session's transcript records (`rate_limit`) and none of the error's text, though `claude -p` exits as the turn ends; on 2.1.325 and earlier, which give a plugin no `$.session.info`, none. `--keep` keeps what was received. The type check runs locally: start one interactive session with `claude --plugin-dir .`, which writes Claude Code's declarations to `.claude-plugin/types/` (gitignored), then run `npx -p typescript@5.6.3 tsc -p .`.

The seated check runs one more `claude -p` session, model mocked, with Claude Code's security default seated: it commits, then sends a prompt whose turn ends on a rate limit. The default is seated only where the machine has managed settings, which apply to every session on it, so the script does nothing unless `MW_E2E_SEATED=1` says the caller wrote them for it. CI writes `/etc/claude-code/managed-settings.json` on its throwaway runner as its last step, runs the check and removes the file; locally, run it in a container (the top of `tests/e2e/seated.mjs` has the command). It fails unless the session's debug log says the default is seated, the plugin loads in the `user` tier with no classic hook, and its tool call, prompt and turn hooks each ran with none reported skipped.

A release bumps the version in both `.claude-plugin/plugin.json` and `hooks/version.ts`.

The redaction packs are Mainwave's, shared with its SDKs and CLI hooks: a change to them there is a change here, in `hooks/packs.ts`, with the sample strings in `tests/pack-vectors.ts` regenerated from the CLI hooks' output.
